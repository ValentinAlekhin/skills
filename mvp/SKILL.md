# MVP

Доводи задачу до работающего MVP с минимальным необходимым набором сервисов.
Следуй явным требованиям пользователя; при доработке проекта сохраняй его
существующие соглашения и не затевай миграцию стека без запроса.

## Стек

- Фронтенд всегда на **Nuxt**, Vue и TypeScript. Компоненты пиши через
  `<script setup lang="ts">`.
- Стек интерфейса выбирай по задаче: кастомный дизайн — **UnoCSS + Reka UI**,
  типовой интерфейс или собственная админка — **Nuxt UI**. Подробности ниже.
- Если требуется управление контентом через CMS, используй **Strapi** с
  TypeScript; для БД по умолчанию PostgreSQL. Без такой потребности не добавляй
  CMS. Серверные задачи небольшого MVP можно решать в Nuxt `server/`.
- Все приложения и необходимые инфраструктурные сервисы упаковывай и запускай
  в **Docker**. Запуск только на хосте не считается завершённой поставкой.
- Выбирай совместимые стабильные версии пакетов и поддерживаемую ими Node.js LTS.
  Фиксируй версии среды и lock-файлы; существующий менеджер пакетов сохраняй.
- Для нового проекта предпочитай Oxlint и Oxfmt. Проверку типов Nuxt выполняй
  отдельно: линтер не заменяет проверку Vue-шаблонов и TypeScript.

## Выбор интерфейса

| Задача | Стек | Как применять |
| --- | --- | --- |
| Кастомный дизайн, собственная дизайн-система, точная реализация макетов | `unocss`, `@unocss/nuxt`, `reka-ui` | UnoCSS для стилей, Reka UI для доступных headless-примитивов; собственные компоненты и оформление. Nuxt-модуль Reka UI — `reka-ui/nuxt`. |
| Типовой продуктовый интерфейс, кабинет, собственная админка | `@nuxt/ui`, `tailwindcss` | Готовые компоненты Nuxt UI с настройкой темы и вариантов. |

Для нового приложения выбирай один из этих вариантов. Не добавляй Nuxt UI
и Tailwind поверх UnoCSS ради отдельных компонентов: в кастомном интерфейсе
используй примитивы Reka UI. Nuxt UI уже основан на Reka UI и Tailwind CSS;
отдельный второй UI-слой ему не нужен. Собственная админка на Nuxt UI не меняет
выбор Strapi, если задаче также нужна CMS.

## Модули фронтенда

Используй этот набор по назначению; условные модули подключай при соответствующих
требованиях. Проверяй, какие модули уже регистрирует выбранная версия Nuxt UI
или Nuxt SEO, и не дублируй регистрацию.

| Назначение | Пакет | Правило |
| --- | --- | --- |
| Утилиты Vue | `@vueuse/core`, `@vueuse/nuxt` | Базовый инструмент фронтенда для готовых composables и их автоимпорта. |
| Общее состояние | `pinia`, `@pinia/nuxt` | Используй Pinia для состояния, разделяемого между компонентами и страницами; локальное состояние оставляй в компоненте. |
| Несколько языков | `@nuxtjs/i18n` | Подключай при мультиязычности; настраивай переводы, локализованные маршруты и метаданные. |
| Иконки | `@nuxt/icon` | Используй локальные npm-коллекции или SVG из assets по правилам ниже. |
| Изображения | `@nuxt/image` | Используй `NuxtImg` / `NuxtPicture` для контентных изображений, настраивай размеры и источники. |
| Динамическая тема | `@nuxtjs/color-mode` | Подключай, когда нужны переключение темы или системная тема; без этого требования отключай автоматическое подключение в Nuxt UI через `ui.colorMode: false`. |
| SEO | `@nuxtjs/seo` | Подключай для публичного сайта; задай URL сайта, метаданные, sitemap и robots. Закрытые разделы исключай из индексации. |
| OG-превью | `nuxt-og-image` + Takumi | Когда нужны OG-превью, генерируй их через Takumi; при подключённом Nuxt SEO не регистрируй OG-модуль повторно. |

Для запросов данных в Nuxt используй его `useFetch` / `useAsyncData`; не подменяй
их одноимённым composable VueUse случайным импортом.

### Иконки и шрифты

Источники иконок и шрифтов — зависимости в `package.json`, а при отсутствии
подходящего пакета — файлы в `client/app/assets/`.

- Для иконок устанавливай нужные коллекции `@iconify-json/*`. Если коллекции
  нет, храни SVG в `client/app/assets/icons/` и подключай их как локальную
  коллекцию Nuxt Icon через `icon.customCollections`.
- Для шрифтов используй пакеты `@fontsource/*` или `@fontsource-variable/*`
  и импортируй CSS только нужных начертаний и наборов символов. Если пакета нет,
  храни файлы в `client/app/assets/fonts/` и объявляй `@font-face` в локальном CSS.
- Не подключай шрифты и иконки через CDN, внешние CSS-импорты или публичные API.
  В Nuxt UI отключай автоматическое подключение Nuxt Fonts через `ui.fonts: false`.
- Nuxt Icon настраивай на локальные коллекции и отключай fallback к публичному
  Iconify API (`icon.fallbackToApi: false`). Для серверной сборки явно выбирай
  локальный server bundle; для статической — включай все используемые иконки
  в client bundle, в том числе динамические имена и иконки компонентов Nuxt UI.
- Проверяй, что иконки и шрифты попали в production-сборку и работают без
  обращений к внешним сервисам. Локальные шрифты используй и в OG-шаблонах.

### OG-превью на Takumi

Takumi — renderer для Nuxt OG Image. Для Node.js в Docker подключай
`@takumi-rs/core` и создавай шаблоны `app/components/OgImage/*.takumi.vue`.
Проверяй поддержку выбранного базового образа и архитектуры процессора.
Если изображения генерируются во время запросов, включай нативный binding,
шрифты и прочие runtime-ресурсы в финальный образ; не полагайся на devDependencies
сборочной стадии. Настрой необходимые выбранной версии OG-модуля runtime-секреты
через окружение. Проверяй реальный URL OG-изображения в production-контейнере.

### Дополнения по задаче

Подключай только при необходимости, а не как обязательный стартовый набор:

| Потребность | Пакет | Условие |
| --- | --- | --- |
| Сложные кастомные формы, массивы полей, многошаговый ввод | `vee-validate`, `@vee-validate/nuxt` + Zod | Переиспользуй схемы из `common/`, выбирай совместимые версии. Для обычной формы Nuxt UI сначала используй `UForm` с Zod без второго движка форм. |
| Собственная авторизация с серверными сессиями | `nuxt-auth-utils` | Требуется Nuxt server; не добавляй независимую вторую систему авторизации поверх уже выбранной CMS или провайдера. |
| Внешние скрипты аналитики, карт, чатов, видео | `@nuxt/scripts` | Подключай при наличии таких интеграций и настраивай момент загрузки. Правило локальных шрифтов и иконок сохраняется. |

## Монорепозиторий

Размещай приложения и общий пакет рядом:

```text
client/                 # Nuxt
  app/components/
  app/pages/
  app/composables/
  app/stores/
  app/assets/css/
  server/               # API и серверная логика Nuxt, если нужны
  public/
  Dockerfile
cms/                    # Только если нужна CMS
  src/api/
  src/components/
  config/
  Dockerfile
common/                 # Реально используемый общий код
  src/
  package.json
.dockerignore
```

Не создавай пустые сервисы и пакеты ради структуры. В существующем репозитории
сохраняй расположение приложений; общий код выноси в `common/`.

`common/` — отдельный приватный пакет с общими типами, схемами валидации,
константами и бизнес-правилами. Импортируй его через имя пакета вида
`@<project>/common`, а не относительными путями в исходники соседнего приложения.
Zod подходит для схем, которые должны одинаково работать в браузере, Nuxt API
и CMS. Не помещай в общий браузерный пакет секреты, доступ к БД и серверные зависимости.

Обеспечь сборку `common` до сборки и запуска зависимых приложений. В режиме
разработки добавь watch или явно опиши пересборку после изменений. Проверяй
совместимость модулей: если потребителям нужны ESM и CommonJS, собирай оба
формата с декларациями типов и корректным `exports`. Если приложение сохраняет
ссылку на пакет в production, включай его сборку и runtime-зависимости в образ.

## Docker

- Делай многостадийные образы приложений с отдельными стадиями установки,
  сборки и запуска. Зависимости устанавливай по lock-файлу.
- Когда сборке нужен `common/`, используй корень монорепозитория как контекст:
  `docker build -f client/Dockerfile .` и, при наличии CMS,
  `docker build -f cms/Dockerfile .`.
- В корневом `.dockerignore` исключай локальные зависимости, артефакты сборки,
  `.git` и секреты. Не исключай исходники и lock-файлы, нужные для сборки.
- Для Nuxt используй production-сборку: `.output` в серверном режиме или
  статическую генерацию, если её достаточно для задачи. Strapi запускай после
  сборки админки в production-режиме. Сервисы в контейнерах слушают `0.0.0.0`.
- Данные PostgreSQL и загрузки CMS сохраняй в volumes либо подходящем постоянном
  хранилище. Конфигурацию и секреты передавай через окружение; добавляй только
  безопасные `.env.example`, без рабочих значений.
- Дай воспроизводимую команду запуска всех нужных контейнеров. Для нового проекта
  обычно достаточно Docker Compose; существующий способ оркестрации сохраняй.
  Учитывай готовность БД перед запуском CMS.

## Интеграция Nuxt и CMS

Переиспользуй общие схемы и правила из `common/` на клиенте и сервере; входные
данные проверяй на серверной границе независимо от браузерной проверки.

Токены CMS и другие секреты храни в приватном `runtimeConfig` Nuxt и используй
только на сервере. В `runtimeConfig.public` помещай лишь общедоступные значения.
Различай внутренний адрес CMS в Docker-сети и URL, доступный браузеру; имя
контейнера не является публичным адресом.

При изменении схем Strapi обновляй генерируемые типы и потребителей API. Права
доступа к контенту и загрузкам настраивай под требуемые сценарии.

## Порядок работы и готовность

Сначала определи основной пользовательский сценарий, тип интерфейса, нужна ли
CMS и какие данные общие. Просмотри текущие инструкции проекта, зависимости и Docker-файлы,
если проект уже существует. Затем реализуй минимальный сквозной сценарий,
включая UI, необходимые API, хранение данных и контейнерный запуск.

Проверь типы, линтинг, форматирование и production-сборку затронутых пакетов.
Выполни существующие релевантные тесты; добавляй новые там, где они проверяют
существенное поведение. Собери Docker-образы и проверь основной сценарий через
контейнеры; при наличии CMS проверь также её связь с БД и сохранность данных
после перезапуска без удаления volumes.

В документации проекта оставь команды настройки, сборки и запуска, необходимые
переменные окружения и порядок сборки общего пакета. В результате сообщи, что
работает и что проверено. Если Docker или другая проверка недоступны, прямо
обозначь, какие проверки остались невыполненными.

## Коммиты

Используй **Conventional Commits**: `<type>[optional scope][!]: <description>`.
Выбирай тип по смыслу изменения: `feat`, `fix`, `docs`, `refactor`, `perf`,
`test`, `build`, `ci`, `chore`, `style` или `revert`. Scope указывай, когда он
помогает обозначить часть монорепозитория, например `client`, `cms`, `common`
или `deploy`. Несовместимые изменения отмечай `!` перед двоеточием или футером
`BREAKING CHANGE: ...` с объяснением.

Примеры: `feat(client): add theme switcher`,
`fix(common): validate phone numbers`, `docs: update setup instructions`.
