# MVP

Доводи задачу до работающего MVP с минимальным необходимым набором сервисов.
Следуй явным требованиям пользователя; при доработке проекта сохраняй его
существующие соглашения и не затевай миграцию стека без запроса.

## Стек

- Фронтенд всегда на **Nuxt**, Vue и TypeScript. Компоненты пиши через
  `<script setup lang="ts">`.
- Для интерфейса по умолчанию используй Tailwind CSS и Nuxt UI. Подключай Pinia,
  VueUse, `@nuxt/image`, i18n и другие модули, когда они нужны функциональности.
- Если требуется управление контентом через CMS, используй **Strapi** с
  TypeScript; для БД по умолчанию PostgreSQL. Без такой потребности не добавляй
  CMS. Серверные задачи небольшого MVP можно решать в Nuxt `server/`.
- Все приложения и необходимые инфраструктурные сервисы упаковывай и запускай
  в **Docker**. Запуск только на хосте не считается завершённой поставкой.
- Выбирай совместимые стабильные версии пакетов и поддерживаемую ими Node.js LTS.
  Фиксируй версии среды и lock-файлы; существующий менеджер пакетов сохраняй.
- Для нового проекта предпочитай Oxlint и Oxfmt. Проверку типов Nuxt выполняй
  отдельно: линтер не заменяет проверку Vue-шаблонов и TypeScript.

## Монорепозиторий

Размещай приложения и общий пакет рядом:

```text
client/                 # Nuxt
  app/components/
  app/pages/
  app/composables/
  app/stores/
  app/assets/css/
  server/               # API и серверная логика Nuxt, если нужны
  public/
  Dockerfile
cms/                    # Только если нужна CMS
  src/api/
  src/components/
  config/
  Dockerfile
common/                 # Реально используемый общий код
  src/
  package.json
.dockerignore
```

Не создавай пустые сервисы и пакеты ради структуры. В существующем репозитории
сохраняй расположение приложений; общий код выноси в `common/`.

`common/` — отдельный приватный пакет с общими типами, схемами валидации,
константами и бизнес-правилами. Импортируй его через имя пакета вида
`@<project>/common`, а не относительными путями в исходники соседнего приложения.
Zod подходит для схем, которые должны одинаково работать в браузере, Nuxt API
и CMS. Не помещай в общий браузерный пакет секреты, доступ к БД и серверные зависимости.

Обеспечь сборку `common` до сборки и запуска зависимых приложений. В режиме
разработки добавь watch или явно опиши пересборку после изменений. Проверяй
совместимость модулей: если потребителям нужны ESM и CommonJS, собирай оба
формата с декларациями типов и корректным `exports`. Если приложение сохраняет
ссылку на пакет в production, включай его сборку и runtime-зависимости в образ.

## Docker

- Делай многостадийные образы приложений с отдельными стадиями установки,
  сборки и запуска. Зависимости устанавливай по lock-файлу.
- Когда сборке нужен `common/`, используй корень монорепозитория как контекст:
  `docker build -f client/Dockerfile .` и, при наличии CMS,
  `docker build -f cms/Dockerfile .`.
- В корневом `.dockerignore` исключай локальные зависимости, артефакты сборки,
  `.git` и секреты. Не исключай исходники и lock-файлы, нужные для сборки.
- Для Nuxt используй production-сборку: `.output` в серверном режиме или
  статическую генерацию, если её достаточно для задачи. Strapi запускай после
  сборки админки в production-режиме. Сервисы в контейнерах слушают `0.0.0.0`.
- Данные PostgreSQL и загрузки CMS сохраняй в volumes либо подходящем постоянном
  хранилище. Конфигурацию и секреты передавай через окружение; добавляй только
  безопасные `.env.example`, без рабочих значений.
- Дай воспроизводимую команду запуска всех нужных контейнеров. Для нового проекта
  обычно достаточно Docker Compose; существующий способ оркестрации сохраняй.
  Учитывай готовность БД перед запуском CMS.

## Интеграция Nuxt и CMS

Переиспользуй общие схемы и правила из `common/` на клиенте и сервере; входные
данные проверяй на серверной границе независимо от браузерной проверки.

Токены CMS и другие секреты храни в приватном `runtimeConfig` Nuxt и используй
только на сервере. В `runtimeConfig.public` помещай лишь общедоступные значения.
Различай внутренний адрес CMS в Docker-сети и URL, доступный браузеру; имя
контейнера не является публичным адресом.

При изменении схем Strapi обновляй генерируемые типы и потребителей API. Права
доступа к контенту и загрузкам настраивай под требуемые сценарии.

## Порядок работы и готовность

Сначала определи основной пользовательский сценарий, нужна ли CMS и какие
данные общие. Просмотри текущие инструкции проекта, зависимости и Docker-файлы,
если проект уже существует. Затем реализуй минимальный сквозной сценарий,
включая UI, необходимые API, хранение данных и контейнерный запуск.

Проверь типы, линтинг, форматирование и production-сборку затронутых пакетов.
Выполни существующие релевантные тесты; добавляй новые там, где они проверяют
существенное поведение. Собери Docker-образы и проверь основной сценарий через
контейнеры; при наличии CMS проверь также её связь с БД и сохранность данных
после перезапуска без удаления volumes.

В документации проекта оставь команды настройки, сборки и запуска, необходимые
переменные окружения и порядок сборки общего пакета. В результате сообщи, что
работает и что проверено. Если Docker или другая проверка недоступны, прямо
обозначь, какие проверки остались невыполненными.
